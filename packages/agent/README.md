# Agent 模块

独立于网页和完整游戏引擎的 TypeScript 模块。通过 `MatchPort` 读取已投影的席位观察，执行带身份／版本／请求 ID 的工具请求。

## 1. 运行与验证

在仓库根目录使用 Node.js 22.23.2 或更高版本：

```sh
npm ci
npm run check
npm test
npm run validate:agent
```

最后一条命令会实际请求 GPT-6.1 Terra，使用本地已有的 ChatGPT／Codex 文件凭证，固定 `medium`、`service_tier=default`（非 fast），消耗相应模型用量。每次运行一组场景，结果写入 `artifacts/agent-validation/<run-id>/`。

验证使用合成测试卡和晚局片段的牌桌测试端口，检查工具循环、反馈纠错、投币结果依赖、断连后恢复、上下文压缩、按需裁判及长期策略版本。

## 2. 模型配置

后端配置样例见[agent.example.json](../../system/agent.example.json)。`loadModelConfig` 验证 JSON，`createModel` 创建统一 `ModelGateway`。模型与认证引用由服务端单独配置。

本地模式 `connection.kind=local_codex_credentials` 每次请求读取凭证文件，默认使用 `CODEX_HOME` 或 `~/.codex` 下的 `auth.json`，可用绝对 `authFile` 指定。旧版 Codex 登录令牌使用配套的 Codex Responses HTTP 协议；若部署持有另一授权流程的令牌，可明确配置相匹配的 `baseUrl`。模型请求及提示词、工具、会话和记忆由本模块管理。

凭证的刷新与续期由外部认证管理者维护。文件更新后，下一次请求重新读取；过期或缺失时返回错误，401 按重试预算重新读取文件。

OpenAI 兼容模式的配置示例：

```json
{
  "schemaVersion": 1,
  "model": "gpt-6.1-terra",
  "reasoningEffort": "medium",
  "fast": false,
  "connection": {
    "kind": "openai_compatible",
    "baseUrl": "https://example.com/v1",
    "apiKeyEnv": "PTCG_MODEL_API_KEY",
    "protocol": "chat_completions"
  }
}
```

`protocol` 可选 `responses` 或 `chat_completions`；服务须支持配置的函数工具与模型参数。认证值从引用的环境变量取得。请求关闭跨地址重定向；Responses 流以 `response.completed` 标记完成。调用轨迹保存脱敏后的请求和响应正文。

流式片段默认按 64 KiB 或 100 毫秒批量同步写盘；请求开始、完整返回、失败和工具记录等其他事件是持久屏障，返回前同步保存全部前缀。写入失败会阻止后续关键记录成功返回，完整模型返回尚未持久化时不会执行牌桌操作。进程强制退出可能丢失尚在缓冲区的末尾流片段，原请求与已经返回的关键记录保持持久保证；独立使用 `JsonlTrace` 时可调用 `flush()` 等待清空。

## 3. 核心接口

| 接口 | 用法 |
| --- | --- |
| `AgentRuntime.create / activate` | 一局一席位固定卡组、策略与规则；每次决策调用一个函数，可提交顺序操作序列；遇新信息或失败再决策。等待对手时不调用模型 |
| `MatchPort.observe / execute` | 游戏端提供真实状态投影与幂等执行，负责提交校验、操作权和正式结果 |
| `FileSessionStore / JsonlTrace` | 副作用前持久保存原请求；断连保留 pending，重建 agent 后复用同一 ID。全部可取得模型输入／输出、工具尝试及失败留档 |
| `AgentRuntime.compact / judge / summarize` | 压缩仅处理自身资料；裁判每个异议独立上下文并校验证据／恢复点；总结仅使用本席位观察和反馈 |
| `AgentRuntime.initializeStrategy / StrategyRepository` | 初始化实际请求模型，以完整卡组和冻结规则生成整局计划；JSON 保存计划和历史，按更新 ID／基础版本发布，新局固定版本；冲突须基于最新版重新总结 |

正式提示词位于 [system/prompts.json](../../system/prompts.json)，四套角色、工具说明和反馈均可配置。`loadPrompts(path?)` 校验并根据全部内容计算版本，宿主在建局时保存完整快照；新建局才读取更新。`loadDefaultPrompts()` 提供默认副本，旧 [Markdown 模板](./prompts/) 保留作为历史验证来源。协议类型见 [types.ts](./src/types.ts)，模型连接见 [model.ts](./src/model.ts)，运行循环见 [runtime.ts](./src/runtime.ts)。

`activate` 的返回包括 `waiting`、`finished` 和 `aborted`。取消时停止提交新操作，结果待定的原请求以 pending 保存，供后续显式恢复。对局胜负由牌桌端的结果确认流程处理，完整事件、恢复与部署由游戏服务负责。

## 4. 决策与上下文预算

每次决策可以调用单个工具，也可以通过 `execute_sequence` 提交最多 16 个操作。宿主按顺序执行，每步使用实际新版本和独立请求 ID；仅当 `ToolReceipt.continuation=continue` 时继续。抽牌、开牌、随机、交权、非机械的流程变化或拒绝会停止后缀；仅进入检查阶段且操作权未变时，已经确定的检查和交还下一方步骤可同批继续，反馈列明已完成结果和未执行项。序列不是事务，成功部分不会回滚；取消及断连后保存序列进度，待定请求沿用原 ID 重试。单步模式同时将 `maxActionsPerDecision`、`maxToolCallsPerActivation` 设为 1，恢复旧序列也只处理一步。

每个压缩段只装配一次固定卡组／启用策略和 snapshot 基准；后续用 snapshotUpdates 路径替换重建当前牌桌。已发送消息与定义只追加，成功压缩才换段，断连重试不重写旧前缀。成功玩家推理已消费的可压缩历史超过 80,000 UTF-8 字节时，压缩器只接收上次成功压缩后的已消费观察／工具记录与已有摘要；原始记录完整留存。尚未消费的新输入先完整交付一次，不因其体积提前压缩；每段当前快照基准与旧摘要作为固定成本单独计量。实际动态输入可暂时超过该触发值，轨迹记录压缩前后大小、可压缩量和覆盖量。压缩只覆盖成功玩家推理已消费的观察和工具前缀，`memoryCoverage` 标明该水位；已摘要前缀不再重放。尚未被一次成功玩家推理消费的消息完整保护，失败和重建不会提前移除工具结果。`recentHistoryBytes` 仅为旧配置兼容保留。摘要正文与引用共同受字节预算限制。旧上下文在首次模型决策前先摘要历史快照中的已知事实，避免迁移时丢失曾见过的信息。

历史查询默认返回近期记录，普通页同时受条数和约 24 KB 字节限制；用 `after=cursor` 向后续事件翻页，`before=previousCursor` 查询更早事件。异常大单条完整返回并明确标记。压缩与赛后总结仅将已经存在于本席位观察中的查询结果替换为索引，不修改原始记录，也不移除查询带来的新事实。

增量压缩通过 `retrievedObservations` 提供本批查询重新取回的旧观察，保留正在核对的事实，原始观察的增量水位保持向前推进。玩家、压缩和复盘输入中的相同牌面通过 `knownCards` 与稳定内容引用共享，卡牌实例、位置和数量保持原样。动态历史预算计算事实和引用，牌面表独立提供；摘要和策略使用牌名表达。

历史事件使用 `compact-events-v1`：省略与外层重复的身份字段及可重建的命令标签，重复流程通过 `eventFlows` 引用；自定义标签、撤销信息、时间和实例位置保留，当前牌桌由基准及有序替换完整重建。`restoreEvents` 可无损还原，长期摘要不保存内部流程引用。

玩家输入中的 `knownCards` 与 `eventFlows` 按首次引用的位置增量提供，同一输入中的各表累积合并。流程首次出现就使用稳定引用，后续新增卡牌或再次出现相同流程不会重写已有历史。工具反馈中的新牌面资料紧跟反馈提供，调用和反馈保持相邻。工具定义采用稳定全集，execution.availableTools 表示当前权限；普通调用及序列每步仍由宿主授权。压缩换段和提供方缓存策略仍可能缩短缓存前缀。

AI 的当前策略以 `policy.plan` 保存完整长期计划，结构由模型按卡组自主组织。初始化请求模型，并提供完整卡组和冻结规则。赛后基于新信息维护整份计划，旧局部条目和证据支持读取及增量迁移。策略表现可通过手动运行的冻结版本对照比较。

赛后复盘单次输入默认最多 160,000 UTF-8 字节，预留 28% 用于纠错。流程为有界事实提取、原件核验、整份计划维护。复盘复用牌面与事件无损编码，按相同冲突命题分组核验。

检索根据实际操作记录补齐相关回合的本席位观察，包含恢复记录。依据既有 `inPlayFacts` 增量与 `departedInPlayRefs`，在赛后临时还原引用事件的历史公开实例，按值去重并标注 `observedAtEventIds`，追补入场、进化、叠牌及换位来源。历史实例使用对应时点的来源，缺失的旧增量保留为未知。投影标记为 `observed_deltas`／`historicalStateComplete=false`，锚点列于 `partialHistoricalStateAtEventIds`，事实按直接来源记录。

纯事件核验使用 `verificationScope=observed_events`，核对记录与历史实例；涉及主张或推论时一并提供完整规则。核验范围随事实保留在策略输入和轨迹中。超预算来源保留为未决，并记录实际输入大小、覆盖回合和缺失来源。异议理由作为待核实主张提供一次，确认胜负和已执行处置单独投影。旧兼容条目支持 add/revise/suspend/retire，未触及条目和既有证据保留，玩家使用启用中的策略条目。

Responses 工具参数流会检查不可能合法的 JSON 前缀，并检测长度 1 至 16 的单元连续重复 512 次的极端周期输出；这类失败取消流并使用既有有限重试预算。该重复上限也可能拒绝刻意生成的超长周期文本。完整成功响应持久化后执行工具。

压缩引用使用按本席位观察序号生成的稳定短标签（如 `e123`），工具 schema 保持固定，input.allowedEvidenceRefs 限定旧摘要引用与新增观察的可选标签。宿主将引用还原为原始 ID 后校验、计入字节预算并落盘；原始观察不改写。无效引用的反馈包含具体错误标签与可选值，便于模型纠正。

`npm run validate:throughput` 用真实 Terra、medium、非 fast 在独立 `MatchRuntime` 中验证 16 个合成标记操作、两次阶段切换与两次增量压缩，最多 8 次模型调用，总时限 120 秒。源码／规则散列、提示词快照、模型轨迹与结果写入新的 `artifacts/agent-validation/<run-id>/`。

## 5. Token 与缓存统计

本地凭证连接默认发送稳定的会话级 `prompt_cache_key`，按玩家会话及角色分组，复盘分页沿用同一组。OpenAI 兼容连接默认关闭该参数。系统模型配置可设置 `cacheKeyStrategy: "session"` 开启，或 `"disabled"` 关闭；key 由会话和角色散列生成，在各次决策、重试、回合和分页中保持稳定。缓存命中情况通过模型返回的 usage 统计。

```sh
npm run report:usage -- <matchId、对局目录或agent-trace.jsonl路径>
```

生成 `artifacts/token-usage/<时间>/usage.json` 与 `用量统计.md`，可用 `--output <目录>` 指定派生报告位置，不修改原始轨迹。按角色、玩家、HTTP attempt 统计输入、输出、缓存输入、未缓存输入及命中率；模型完成记录也保存标准化 `tokenUsage` 字段。支持本模块 Responses 与兼容 Chat usage 格式。

输入已包含缓存读取和写入，输出已包含推理部分。缓存写入取服务端 `cache_write_tokens`，未报告时保持未知；未缓存输入包含写入，普通输入在读取、写入和总输入三项齐全时相减。缓存 token 命中率为有完整数据请求的缓存输入／输入，另列有缓存请求比例。缺失 usage 标记为未知，失败尝试、字段覆盖率和统计异常单独列出，所有 token 均来自服务端报告。

## 冻结验证与策略迁移

`node scripts/freeze-validation.ts context` 从冻结副本验证真实模型对真假主张、实例替换和顺序变化的核验。`node scripts/freeze-validation.ts throughput` 验证顺序操作及增量压缩。`node scripts/freeze-validation.ts match <对手A ID> <对手B ID>` 复制这两名对手至隔离数据目录，进行一局真实对战并保存模型轨迹、原始上下文、输入输出 token、缓存命中、决策、压缩和耗时。所有验证使用独立副本，文件清单与前后散列位于新建的 `artifacts/frozen-validation/` 目录。

旧文本策略在首次新局激活前追加迁移版本，将提取内容保存为候选并保留旧文。卡组或规则指纹变化时，旧启用项转为候选等待复核；策略按匹配的卡组和规则范围发布。旧上下文由宿主补齐本局冻结规则指纹，独立上下文使用自身可恢复的规则范围。

隐藏洗牌允许与随机顺序无关的固定步骤及本人牌库顶部盲抽；洗牌依赖在中间宣告和重启后仍存在。已知牌面展示可继续；临时查看的位置只在关联区域未变化且未洗牌时沿用。新牌面、未知随机结果、读取反馈、拒绝及操作权或阶段变化仍停止后缀。公开场上时点仅关联当前公开实例，不追踪隐藏区身份，也不判定动作是否合法。

## 手动策略对照

首页「策略评估」选择双方 AI 的精确策略版本及被评估席位，手动运行版本 A；结束后选择该席位的另一策略版本，手动运行版本 B。A 开局前的牌桌、双方卡组、独立随机流、固定对手策略和模型／规则／提示词一并保存，B 复用该起点。源码变化后重新建立起点，以相同实现开展版本对照。

评估期间保留参评策略版本，每局手动启动；普通对局在赛后维护完整计划。隐藏牌序和种子保存在服务端原件，玩家按席位获取观察。随机流按用途、区域和回合隔离，行动分歧后各分支按自身调用推进。可结合多个起点的结果比较策略表现。

相同 eventId 的工具结果和同请求内观察完全一致时，线上反馈可使用 `observationRef` 引用该实际来源；同一请求缺少来源或内容不同时保留全文。原始 native 记录和开牌资料完整保存，引用可逆还原，压缩换段不沿用不可达来源。

## 已定目标检索与短坐标

新配置允许 AI 在检索前确定目标牌面，由 `show_known` / `move_known` 按名称、可选牌面引用及匹配序号定位当前可查看的散牌。一次完整区域查看后，可在同批步骤中展示和移动这些预选目标；目标不可用时停止并交还 AI 选择，不选替代牌。默认匹配当前第一个符合条件的已知散牌；不同版本可指定 `cardRef`。洗牌、离区、恢复会断开相应私有位置关联，新插入未知牌不会借用旧查看授权。抽牌、随机和操作权变化仍停止后缀。

批量模式仅向模型暴露 `execute_sequence`，避免重复定义原子工具；单步模式保留原子工具。新提示配置显式启用 `ptcg-positions-v1` 时，位置可写 `A:hand/2` 或 `A:active/0/attached/1`。整包参数先严格解码、复验全部标准 schema，再逐步执行；pending、原子请求和牌桌记录保持标准协议。旧局没有编码标记时沿用原参数。

`node scripts/freeze-validation.ts replay-match <已完成冻结对局目录>` 复用一局清空初始化后的 v1 策略、开局前牌序和随机状态，以当前源码与提示词运行一次性能验收。产品内的手动对照则固定源码，比较策略版本。
